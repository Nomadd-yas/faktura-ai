# Агентный чат разбора

Спека фронта: `15-runs.md` §15.9, `12-rag.md` §12.2-12.5. API: `docs/api/CORE_API.md` §4j. Код: `backend/src/faktura/agent/`.

```
POST /runs/{id}/messages -> рабочий поток -> цикл агента (backend) <-> ML POST /llm/chat (ключ RouterAI только там)
                                                 |  инструменты: только чтение данных ЭТОГО разбора
                                                 v
                              проверка (verify) -> сноски [n], cites, cards -> БД (run_messages) -> SSE
                                                 \-> больше половины отброшено / сбой: базовый /ask (§12.1)
```

Решения: агент строится у нас, цикл живёт в бэкенде, в ML только прокси модели. Чат существует только внутри разбора.

## Инструменты (`tools.py`)

Область (`scope`) — статьи разбора — подставляет бэк, модель её не задаёт. Строки берутся так же, как у `/ask`
(`ask.context.load_ctx`): отклонённые строки v2 исключены, исправленные значения подставлены, замечания — открытые.
`results` без дубликатов (`duplicate_of`) и не `extracted`. Каждый результат — компактный JSON ≤ ~14 000 символов.
Колонки таблиц — из реестра области; добавлены виртуальные: `pid` (код статьи, вместо `publication_id`), `id`
(`pid/<ключ>`), у `results` ещё `fact_id` (= `pid/result_id`), `value`/`unit` (действующее нормализованное значение,
иначе исходное), solar: `material_class`, `device_label`; rag: `dataset_name`, `task_type`, `config_name`, модели
конфигурации. Числовые операторы работают по числу в ячейке, `=`/`in` — без регистра, числа — численно.

| Инструмент | Аргументы | Возвращает |
|---|---|---|
| `schema` | — | домен, коды статей, 7 таблиц (колонки, enum из паспорта, виртуальные колонки, число строк), метрики с единицами |
| `filter` | `table, where[{col, op, value}], columns, order_by ("col" / "-col"), limit ≤ 200 (по умолч. 20), pids` | `{total, returned, rows, truncated?}`; у `results` — `fact_id, metric_name, value, unit, …, source_page` |
| `group` | `table, where, by[col], agg[{col, fn}], limit ≤ 50` | группы: `n`, `aggs[{agg_id, fn, col, value, n_values}]` (count всегда), `ids` (до 50), у results `units` и `warning` при смеси метрик/единиц |
| `top` | `table, col, n ≤ 50, dir desc/asc, where, columns` | лучшие строки; для «чем меньше, тем лучше» (Rs, HI, latency) — `dir=asc` |
| `get_row` | `fact_id` ("pid/id") или `table+pid+id` | полная строка с `source_page`, `source_fragment`, названием статьи |
| `get_issues` | `pids, check, limit ≤ 50` | открытые замечания (`id = pid/issue_id`, `check_name`, `description`, `source_page`) |
| `comparable` | `fact_ids[≥2, ≤60]` | группы сопоставимости и список различающихся полей. solar: метрика, единица, агрегация, происхождение + условия измерения (тип, спектр, интенсивность, направление и скорость скана, маска, температура). rag: задача, датасет, split, метрика, вариант, k, единица, происхождение |
| `rules` | `check?` | определения проверок области из паспорта (`passport/data/*.json`) + формулы, пороги и типичные причины: `{check_name, title, description, level, formula?, thresholds?, typical_fix?}` |
| `calc` | `expr, inputs{имя: fact_id \| число}` | безопасная арифметика (`calc.safe_eval`: ast, только числа, имена из `inputs`, `+ - * /`, унарный минус, скобки) -> `{calc_id, value, inputs{имя:{fact_id, value, unit}}, expr}`; маркер `[[calc:calc_id]]` |
| `propose_fix` | `items[{fact_id, suggested, unit?, reason}]` | карточка `fix` с предложенными исправлениями; ничего не применяет, текущее значение берётся из строки |
| `search_text` | `query` (английский), `pids, k ≤ 10` | `faktura.textindex.search_text(uow, corpus_id, query, pids=<область>, k)`; хиты чужих статей отбрасываются |
| `read_page` | `pid, page` | `faktura.textindex.read_page(...)`; цитируется маркером `[[page:<pid>/<page>\|цитата]]` (старый `[[chunk:page:<pid>/<page>\|…]]` тоже проходит) |
| `clarify` | `question, options[2..4]` | не инструмент данных: завершает ход вопросом-уточнением |

`where` ops: `= != > >= < <= in contains is_null`. `limit` > 200 режется до 200. Ошибка аргументов
(неизвестная колонка, оператор, статья не из разбора) возвращается модели как `{"error": …}` — она исправляет вызов.
`textindex` подключается лениво: нет модуля — `search_text` отдаёт `{"results": [], "note": …}`, `read_page` — `{"found": false}`.
Агрегат получает `agg_id` (`a1`, `a2`, …) и список строк-источников; на него ссылаются `[[agg:a2]]`. Вызовы `group`
и их `agg_id` живут в одном ответе; ссылка на агрегат, которого инструмент не выдавал в этом ответе, не проходит проверку.

## Цикл (`loop.py`, `service.py`)

1. `messages = [system(с описанием разбора), история ≤ 6 пар (каждый ответ ≤ 600 символов), вопрос]`.
2. Модель с `tools` (OpenAI-формат). `tool_calls` -> шаг `step` фронту («Запрос к таблице results: metric_name = PCE,
   value > 15», «Группирую таблицу …», «Ищу в тексте статей: …», «Читаю страницу 4 статьи D001», «Проверяю
   сопоставимость 3 значений», «Смотрю замечания»), выполнение, результат — сообщением `tool`.
3. Лимиты: ≤ 12 вызовов инструментов (лишние в одном ходе получают `{error: limit reached}`; после исчерпания следующий
   вызов модели идёт без `tools` — «ответь по тому, что есть»), ≤ 200 строк за вызов, ≤ 40 с на весь ответ
   (вызов модели не начинается, если осталось < 3 с), `max_tokens` = 1800. Флаг остановки читается из БД между шагами и
   перед каждым инструментом.
4. Ответ без `tool_calls` -> текст; `clarify` -> вопрос-уточнение (ответ без проверки).
5. Сбой модели / таймаут / пустой ответ -> запасной базовый ответ (`fallback`).
6. Всё, что случилось (вызовы инструментов, отброшенные пункты и причины, сырой текст модели, токены, стоимость, режим
   `agent|base`, `fallback`), записывается в `run_messages` (`meta`, `tool_log`, `cost`, `cost_currency`). Тот же `meta` (`model, provider, planner, tool_calls, tokens, cost, cost_currency, seconds, dropped, fallback`) кладётся в `answer.meta` и приходит в SSE `done`.

Подсказка (`prompt.py`, английская, ответ — по-русски): отвечать только по результатам инструментов; «нет данных» — так и
сказать; каждое число с маркером сразу после; не пересчитывать единицы; перед сравнением разных статей вызвать
`comparable`; тексты статей английские — запросы `search_text` на английском; неоднозначно — `clarify` (если в разборе одна статья или фронт прислал `pid`, «эта статья» известна — не переспрашивать; подсказка получает строку «пользователь смотрит статью X (название …)»); вопросы о статье («о чём», «объясни», «выводы») — `read_page(pid, 1)` + `search_text` по методу/результатам/выводам и связный русский пересказ 4–8 предложений (до ~10 для объяснений; числа с маркерами из таблиц или текста), табличные ответы остаются краткими; вопросы о согласовании значений — поток `get_issues`/`get_row` -> `rules` -> `calc` -> вероятная причина -> исправленное число + `propose_fix` (агент только предлагает), текст статьи при необходимости, иначе честно «не восстановить из статьи».

## Проверка (`verify.py`, §12.4)

Ответ режется на пункты: строки, внутри — предложения (маркеры с точками не режутся). Для каждого пункта:

1. Каждое число (кроме годов 19xx/20xx, номеров после «стр./табл./рис./Table/Figure/page», порядковых «1-й», нумерации
   списка, кодов вида D001/F1/Recall@5/GPT-4 и чисел из самого вопроса) связано с маркером: сразу после числа (до
   следующего числа, ≤ 40 символов; подряд идущие маркеры тоже), иначе ближайшим перед ним.
2. Маркер указывает на существующий объект: `fact` — строка `results` области (отклонённых нет), `agg` — выданный в этом
   ответе, `chunk` — выданный `search_text`/`read_page` (цитата `|…` — подстрока текста, без учёта пробелов и регистра),
   `issue`, `row` — существуют в области; `page` — страница существует (читалась `read_page` или читается из индекса), цитата обязательна и является подстрокой её текста; `calc` — выдан `calc` в этом ответе.
3. Число совпадает с действующим значением с точностью округления записанной точности (0,5 единицы последнего знака):
   для `fact` — `value`, `normalized_value`, `metric_value`, `spread_value`, `baseline_value`, `n_devices`,
   `sample_size`, `metric_k`, `time_point` (`raw_value` не принимается: у исправленной вручную строки он хранит старое
   значение); «74 %» против доли 0,74 — только если единица строки `fraction|ratio|score|пусто`; для `agg` — значение,
   `n`, число строк и статей; для `chunk` и `page` — число из цитаты или текста фрагмента/страницы (точное); для `calc` — значение расчёта с точностью округления; для `issue`/`row` — число в ячейках.
   Единицы не пересчитываются (900 мВ ≠ 0,9 В).
4. Нарушение: `RAG_UNVERIFIED=drop` (по умолчанию) — пункт отбрасывается (заголовок списка, чьи пункты все отброшены,
   тоже); `mark` — пункт остаётся с «(не подтверждено)» и без сносок.
5. Отброшено больше половины **всех** предложений (заголовки списков не считаются; проза без чисел и маркеров считается и никогда не отбрасывается, поэтому пересказ с несколькими неверными числами не откатывается на шаблон) или текст опустел -> `fallback=verification`.
6. Маркеры заменяются на `[n]` по порядку первого появления (повторы — одна сноска, подряд `[1][2]`), собираются `cites`
   (`n, domain, pid, result_id|issue_id|chunk_id|agg_id…, page, fragment`) и карточки (`results` по цитированным
   значениям и строкам цитированных агрегатов, `issues`, `compare` если вызывался `comparable`).

## Запасной вариант

Базовый `/ask` (`ask.service.answer_question`: планировщик + детерминированный исполнитель + шаблон) — те же карточки
и сноски, переведённые в формат §15.9 (`n`, `result_id`, `issue_id`, `fragment`). К тексту добавляется причина.
Агент выключен или ML не настроен — базовый ответ без пометки.

## ML: `POST /llm/chat` (`ml/pdf-dataset/ask.py`)

Принимает `messages`, `tools`, `max_tokens` (16..2000, по умолч. 1200), `temperature` (0), `reasoning` (false | true |
число токенов), `tool_choice`; отвечает `{message, finish_reason, meta}`. Провайдер **всегда закреплён**:
`extra_body.provider = {order:[ASK_PROVIDER…], allow_fallbacks:false}`; пустой провайдер — `503 not_configured` до обращения
к модели. `reasoning.enabled=false` по умолчанию. Модель: `ASK_AGENT_MODEL` | `ASK_MODEL` | `ROUTERAI_MODEL` | по
умолчанию. Размер `messages` ≤ 150 000 символов, tools ≤ 24. Без повторов. Файл `ask.py` уже копируется обоими
Dockerfile (новых файлов в ML нет).

## Стоимость одного вопроса (оценка, не замер)

Цены по умолчанию в ML — 0,15 / 0,60 **₽** за 1 млн токенов (вход/выход, `ASK_PRICE_IN/OUT`, грубая оценка; если провайдер присылает
`usage.cost`, берётся он — **у RouterAI он в рублях**, поэтому поле называется `cost` + `currency: "RUB"`, а не `cost_usd`). Один вызов модели: подсказка + описание разбора ≈ 1,5–2,5 тыс. токенов, схемы инструментов ≈
1,5 тыс., история ≤ 1,2 тыс., результат инструмента 0,5–4 тыс.; ответ 100–400 токенов.

| Случай | Вызовов модели | Вход, токенов | Стоимость |
|---|---|---|---|
| «лучший КПД» (1 инструмент) | 2 | ≈ 10–14 тыс. | ≈ 0,002 $ |
| сравнение + comparable (3–4 инструмента) | 4–5 | ≈ 30–45 тыс. | ≈ 0,005–0,008 $ |
| тяжёлый (до 12 инструментов, большие выдачи) | 13 | ≈ 150–200 тыс. | ≤ 0,03 $ |
| уточнение | 1 | ≈ 4 тыс. | ≈ 0,001 $ |

Типично 0,002–0,008 $ за вопрос (≈ 1–3 ₽ при текущем курсе), потолок ≈ 0,03 $; время 5–15 с, максимум 40 с.
Базовый `/ask` стоит ≈ 0,0005 $ (два коротких вызова). Фактическая стоимость каждого ответа пишется в `run_messages.cost` (+ `cost_currency = "RUB"`; колонка `cost_usd` устарела и не пишется, новые колонки добавляются `storage.schema.LATE_COLUMNS` в существующие БД).

## `/ask` через агента

`POST /runs/{id}/ask` при включённом агенте отвечает им же (`service.ask_via_agent`): тот же цикл и проверка, но без ветки (история пуста, в `run_messages` ничего не пишется), ответ — `CaseAnswer` с сносками в форме `CaseCite` фронта (`service.ask_cite`). Нет агента или он не справился — прежний базовый планировщик.
