# Полнотекстовый индекс статей прогона

Агент ищет по тексту статей прогона и получает фрагменты со ссылкой на страницу. Векторы не используются: BM25 / полнотекстовый поиск БД.
Код: `backend/src/faktura/textindex/`.

## Интерфейс

```python
from faktura.textindex import search_text, read_page, index_paper

search_text(uow, corpus_id, query, *, pids=None, k=8) -> [{"chunk_id", "pid", "page", "text", "score"}]  # лучшие первыми
read_page(uow, corpus_id, pid, page) -> {"pid", "page", "text", "pages"} | None   # страница целиком, pages - всего страниц
index_paper(uow, corpus_id, paper_id, pid, pages) -> int                          # (пере)индексация, число чанков
```

`pid` - `publication_id` статьи в прогоне (`RunFile.id`). Вместо `crp_...` принимается и `run_...`. Пустой запрос, запрос из одних
стоп-слов, неизвестный прогон или нет индекса -> `[]` / `None`. Удалённые статьи и корпуса в выдачу не попадают.

## Хранилище

| таблица | колонки |
|---|---|
| `text_pages` | seq, corpus_id, paper_id, pid, page, total_pages, text (страница целиком, очищенная) |
| `text_chunks` | seq, id (`<paper_id>:<page>:<chunk_no>`), corpus_id, paper_id, pid, page, chunk_no, text |

Обе таблицы создаёт `create_all` (`storage/schema.py`), внешние ключи на `corpora`/`papers` с `ON DELETE CASCADE`;
`purge_expired` удаляет их строки вместе с корпусом. Полнотекстовая часть создаётся `Database.create_all` -> `textindex.store.ensure_fts`
идемпотентно:

- **SQLite**: виртуальная таблица `text_chunks_fts` FTS5 (внешнее содержимое `text_chunks`, токенайзер `porter unicode61
  remove_diacritics 2`) и триггеры INSERT/DELETE. Ранг - `bm25()`, наружу `score = -bm25` (больше - лучше).
- **PostgreSQL**: generated-колонка `tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', text)) STORED` + GIN-индекс
  `ix_text_chunks_tsv` (`ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`). Ранг - `ts_rank_cd`.
- Нет FTS5 / нет прав на DDL: запасной поиск `LIKE` по словам (число найденных слов + бонус за фразу); предупреждение в логе.

## Нарезка

Текст страницы чистится (`chunking.clean_text`): лигатуры `ﬁ ﬀ ﬂ ﬃ ﬄ` -> буквы, мягкие переносы и неразрывные пробелы убираются,
перенос по дефису на конце строки склеивается (`exhib-\nits` -> `exhibits`), пробелы схлопываются, абзацы разделены пустой строкой.
Затем - чанки ~1200 символов с перекрытием ~150 по границам абзацев, потом предложений, потом слов. **Чанк принадлежит одной
странице**, страницы не склеиваются. Пустая страница даёт строку в `text_pages` (для `pages` и `read_page`), но не чанки.

## Откуда текст страниц

1. **Текстовый слой PDF**: PyMuPDF `page.get_text("text")` по страницам (под общим `PDF_LOCK`); подряд идущие одинаковые строки
   (двойная печать) схлопываются.
2. **OCR из ML** (сканы). ML-сервис `pdf-dataset` кладёт в `meta.page_texts` список строк (индекс 0 = страница 1) из постраничного
   markdown glmocr; страницы, взятые из текстового слоя при `TEXT_SOURCE=auto|pdf`, отдаются пустыми. Поле едет и в JSON-ответе, и в
   заголовке NDJSON (`header.meta`), формат ответа не менялся. Бэк (`ml/response.page_texts`, `GenericOutcome.page_texts`,
   `ExtractOutcome.page_texts`) берёт его и для страниц, где текстовый слой короче 50 символов, подставляет OCR-текст
   (HTML-теги таблиц вырезаются). Мок-экстрактор `page_texts` не отдаёт - индекс строится только из PDF.

Индексация вызывается после успешного разбора статьи: `PaperProcessor._process_pdf` (solar, режим `full`) и
`GenericProcessor._process_pdf` (rag) -> `textindex.sources.index_pdf` в отдельной транзакции; сбой индексации логируется и разбор не
роняет. Повторный разбор заменяет страницы и чанки статьи (`replace_paper`).

## Запрос

`store.query_terms`: нижний регистр, слова `[^\W_]+`, стоп-слова и одиночные буквы отброшены, до 24 слов. Дальше слова и фразы
(пары соседних слов, при 3..8 словах - вся фраза) соединяются через OR: FTS5 - `"w1" OR "w2" OR "w1 w2"`; PostgreSQL -
`'w1' | 'w2' | ('w1' <-> 'w2')` через `to_tsquery('english', ...)`. Слова содержат только буквы и цифры и заключаются в кавычки,
поэтому операторы и знаки из пользовательского ввода (`"`, `*`, `NEAR`, `:`, `'`, `;`) синтаксиса запроса не меняют. Фильтры по
`corpus_id`, необязательному `pids` и `papers.deleted_at IS NULL` - параметрами.

## Индексация существующих прогонов

- CLI: `faktura textindex rebuild [--run RUN_ID] [--db URL] [--storage-dir DIR] [--only-missing]` - строит индекс из PDF файлового
  хранилища (текстовый слой) для одного или всех прогонов; повторный запуск заменяет данные. OCR-текст сканов в индекс попадает
  только при разборе (в хранилище он не сохраняется), поэтому для сканов rebuild даёт то, что есть в текстовом слое.
- Лениво: первый `search_text` / `read_page` по прогону достраивает индекс для разобранных статей без индекса (PDF берётся из
  файлового хранилища, зарегистрированного `build_services`), не дольше 10 с; остальное - командой rebuild. Статья, PDF которой
  прочитать не удалось, повторно не пробуется до перезапуска процесса.

## Производительность

Прогон из 21 статьи dev (979 чанков, 212 страниц), SQLite: поиск 3-12 мс. Построение индекса при разборе - десятки миллисекунд на
статью (чтение текстового слоя PyMuPDF), ленивая индексация 21 статьи - порядка 2-3 с.
