# Ответ сервиса извлечения потоком (NDJSON)

Спека BACKEND_ONLY §10: «Ответ сервиса извлечения принимать потоком (NDJSON) и писать пачками». Нужно для больших статей
(rag, D014: ~28 тыс. строк `results`): не собирать ответ одной строкой в 50+ МБ и не держать лишние копии.

## Обмен

Запрос тот же (`POST /extract` у pdf-dataset, `POST /ml/extract` у контрактного ML-1), добавляется одно из:

- заголовок `Accept: application/x-ndjson` (клиент бэка шлёт `application/x-ndjson, application/json;q=0.5`);
- поле формы `stream=ndjson` (клиент бэка шлёт и его: прокси иногда режут `Accept`). `stream=json` принудительно
  возвращает обычный JSON. Поле сильнее заголовка.

Без них сервис отвечает как раньше — одним JSON-объектом (режим по умолчанию, совместимость).

Ответ: `200`, `Content-Type: application/x-ndjson`, по объекту JSON на строку, у каждого поле `type`:

```
{"type":"header","protocol":"ndjson/1","ok":true,"model_version":"pdf-dataset/…","publication_id":"D014",
 "extract_error":null,"failed_tables":[],"has_dataset":true,"out_dir":"/out/D014","meta":{…ocr_confidence, suggested_domain…}}
{"type":"table","table":"publications","rows":[{…}]}
{"type":"table","table":"results","rows":[ … до 1000 строк … ]}
{"type":"table","table":"results","rows":[ … ]}
{"type":"end","counts":{"publications":1,"results":28000,"issues":12},"ok":true}
```

- Заголовок — всё, что в обычном ответе, кроме самих таблиц (`dataset`); таблицы идут строками `table` по ≤1000 строк
  (`ML_NDJSON_ROWS` в сервисе pdf-dataset), порядок таблиц любой, пустые таблицы можно не слать.
- Контрактный ML-1 (§7.0.1): заголовок содержит те же верхнеуровневые поля (`model_version`, `warnings`,
  `ocr_confidence`, …), поле `layout` = `flat` (одиночная `publication` едет как таблица `publications` из одной строки,
  клиент собирает её обратно) или `nested` (rag: `tables: {...}`).
- Конец — строка `end`; `counts` сверяются с числом принятых строк. Поток без `end` и без `error` — обрыв.

### Ошибки

- До первого байта ответа (проверка PDF, домен, OCR недоступен, лимит ключа и т. п.) — обычный HTTP-статус и тело
  `{"code","message","retryable","detail"}` (как в JSON-режиме; `Retry-After`, ретраи бэка работают без изменений).
- После заголовка ответ уже `200`, поэтому сбой идёт строкой потока в той же форме:
  `{"type":"error","code":"ml_error","message":"…","retryable":false,"detail":"…"}` — и поток закрывается без `end`.
  Бэк разбирает её как HTTP-ошибку: `pdf_*` → код файла, `retryable=true` → `ml_unavailable` с ретраем, иначе `ml_error`.
- Обрыв соединения / поток без `end` → `ml_unavailable` (ретраится как потеря связи); нарушение формата или несовпадение
  счётчиков → `ml_schema_mismatch`.

## Сторона бэка

- `faktura.ml.ndjson` — формат (`events_from_raw`, `read_stream`, `assemble_body`); `HttpExtractor` запрашивает поток и читает
  `iter_lines()`, строки таблиц накапливаются по мере прихода, обычные адаптеры (`pdf_dataset_to_generic` и т. д.)
  получают тело, эквивалентное JSON-ответу.
- Режим: `FAKTURA_EXTRACT_STREAM=ndjson|json` (по умолчанию `ndjson`). При `ndjson` клиент откатывается на обычный JSON,
  если сервис ответил `406`, и запоминает это до перезапуска; ответ `200` с `Content-Type` не NDJSON (старый сервис,
  игнорирующий `Accept`) разбирается как JSON без отката.
- Запись: `sub_rows` пишется пачками по 1000 (`SubRowsRepo.replace` не строит список всех строк); после проверки
  `GenericProcessor` освобождает сырые строки ответа (`out.tables`, `out.raw`), остаётся одна копия — проверенные таблицы.
- Проверка ответа (`ml/validate.py` для solar, `validate_tables` для rag) идёт **после** сборки потока, по таблицам целиком:
  дубли id, висячие ссылки и циклы `duplicate_of` нельзя проверить по пачке. Пиковая память — одна копия строк плюс
  одна пачка, а не «JSON-строка + разобранный объект + копии».
- Мок (`faktura.ml.mock_server`, `POST /ml/extract`) отдаёт оба режима, ответ в потоке эквивалентен JSON (тест
  `tests/adapters/test_ml_ndjson.py`).

## Метаданные файла в ответе

Сервис кладёт в `meta` (контрактный ML-1 — на верхний уровень ответа) два необязательных поля; бэк сохраняет их в файле
разбора и отдаёт в `RunFile` и сводке статьи (CORE_API §2, §4c, §5):

- `ocr_confidence` — число 0..1, надёжность текста файла: среднее по страницам; страница из текстового слоя PDF — 1.0 (ok),
  0.5 (poor), 0.2 (none); страница glmocr — средний `confidence`/`score` блоков, если распознаватель их отдаёт, иначе
  `0.9 × (1 − min(1, 5 × доля мусорных символов «�»/(cid:N)))`; пустая страница после OCR — 0.5. Подробности —
  `meta.ocr_confidence_basis` (`method`, `pages`, `pdf_pages`, `ocr_pages`).
- `suggested_domain` — `"rag"` | `"solar"` | `null`: заполняется моделью на шаге `publications` только при `in_scope=false`
  и только если статья, вероятно, из другой области (прочие значения и совпадение с запрошенной областью отбрасываются).
  Поле есть в схеме ответа шага, но не в строке `publications` (шаблоны фиксированы): сервис снимает его перед сохранением.

Мок выводит их детерминированно: `ocr_confidence` — доля страниц PDF с текстовым слоем; статья, которой нет в эталоне
запрошенной области, но есть в эталоне другой (например, `D011` в `solar`), приходит как `in_scope=false` с
`suggested_domain` = другая область.
