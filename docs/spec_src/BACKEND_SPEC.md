# Фактура AI — спецификация бэкенда

Документ для бэкенд-разработчика, который не видел интерфейс. Прочитав его, можно сделать API, которое полностью кормит прототип из `src/` (Vue 3, все данные сейчас зашиты в `src/data.ts`, `src/store.ts`, `src/refs.ts`, `src/structure.ts`, `src/gold.ts`).

Основа — ТЗ хакатона ВИНИТИ РАН «Извлечение и структурирование данных из научных публикаций» (две предметные области: тонкоплёночные солнечные элементы и RAG). Поля из ТЗ перенесены с **точно теми же именами** (`publication_id`, `device_id`, `metric_value`, `extraction_status` и т. д.). Всё, что сверх ТЗ, взято из интерфейса.

## 0. Соглашения

**Базовый путь:** `/api/v1` (так в примерах на экране «Экспорт и API», `src/views/ExportView.vue`: `https://api.faktura.ai/api/v1/...`). Все пути ниже даны без префикса: `GET /papers` = `GET /api/v1/papers`.

**Формат.** JSON, UTF-8. Имена полей — `snake_case`. Числа — числами с точкой (`18.6`), форматирование с запятой («18,6 %») делает фронт. Даты — ISO 8601 в UTC (`2026-11-20T09:15:00Z`). Идентификаторы — непрозрачные строки (рекомендуемый вид `pap_8f3k2x`, `fct_...`); фронт не разбирает их по частям.

**Авторизация запросов.** `Authorization: Bearer <access_token>` (см. §2). Без токена открыты только `POST /auth/login`, `POST /auth/refresh`, `GET /health`.

**Пагинация.** Списки отдают

```json
{ "data": [ ... ], "total": 42, "next_cursor": "eyJvIjoyMH0" }
```

Параметры: `limit` (по умолчанию 50, максимум 500), `cursor` (из `next_cursor`). Где порядок важен для интерфейса, есть `sort` и `dir` (`asc|desc`). Короткие справочные списки (коллекции, правила, разделы паспорта) отдаются целиком без пагинации, но в той же обёртке `{ "data": [...] }`.

**Ошибки.** Любая ошибка — HTTP-код из §8 и тело

```json
{
  "error": {
    "code": "fact_value_unrecognized",
    "message": "Не удалось распознать значение «1,1 кВ»: единицы «кВ» нет в словаре для параметра «Voc».",
    "field": "raw",
    "details": { "unit": "кВ", "param": "voc" }
  }
}
```

`message` — всегда на русском и пригоден для показа человеку (интерфейс показывает его в уведомлении или под полем). `code` — стабильный машинный код. Полный список — §8.

**Действие и отмена.** Каждый изменяющий запрос (принять факт, разобрать замечание, удалить чат…) пишет запись в журнал действий и возвращает её идентификатор в заголовке `X-Action-Id` и в поле `action_id` ответа. По нему работает «Отменить» в уведомлении (§4, «История и отмена»).

**Источник данных.** Каждое поле сущности и каждый эндпоинт помечены источником:
- **[ML]** — извлечено или сгенерировано моделью ML-сервиса (§7); бэк проверяет, нормализует и сохраняет, но сам значение не придумывает;
- **[BE]** — вычислено бэком детерминированно (идентификаторы, время, нормализация, проверки, счётчики, агрегаты, поиск);
- **[USER]** — введено или выбрано пользователем (имя проекта, принятие факта, исправленное значение, синоним, вопрос в чате);
- **[FE]** — живёт только в браузере, бэк не участвует (внешний вид, клавиши, раскладка графа).

Комбинации пишутся через «→»: `[ML]→[BE]` — сырьё от модели, итог считает бэк (например, `raw_value` [ML] → `normalized_value` [BE]); `[ML]|[USER]` — от модели или (у ручных фактов) от человека.

**«В интерфейсе появится».** Поле или функция есть в ТЗ, но в прототипе пока не показаны. Бэк их всё равно хранит и отдаёт.

## 1. Обзор

### 1.1. Что за продукт

«Фактура AI» извлекает структурированные данные из корпуса научных PDF: по заданному списку полей (PCE, Voc, Jsc, FF, слои, условия; для RAG — конфигурации и метрики) находит значения, пишет их в связанные таблицы ТЗ с указанием страницы, таблицы/рисунка и фрагмента, нормализует единицы, проверяет правилами, даёт искать и фильтровать по всей таблице и выгружает набор данных с паспортом.

#### 1.1.1. Основной поток — пакетная обработка корпуса

Организаторы (кейс 5, материалы в `docs/case5/`) дали корпус области 1: `dev/` — 21 PDF с эталоном `dev_gold/`, `test/` — 90 PDF (`P001`…`P090`), **по ним идёт оценка**. Сдаются **ровно 7 CSV** шаблона (`publications`, `materials`, `devices`, `layers`, `measurements`, `results`, `issues`), их проверяет `tools/check_submission.py`. Поэтому главный сценарий — пакетный, а не чат по одной статье. Подробно — [§13](spec/13-corpus.md), формат — [§14](spec/14-submission.md). Архива по области 2 (RAG) нет — её формат сдачи уточнится позже.

```
1. Вход → экран «Корпус» (/corpus)                              GET /corpus/overview
2. Импорт: папка / ZIP / список URL → дедупликация              POST /corpora, POST /corpora/{id}/files
3. Прогон по профилю полей (список полей = паспорт)            POST /corpora/{id}/runs  → ML разбирает каждый PDF
4. Бэк нормализует и проверяет каждую статью                   этапы «Нормализация», «Проверка»
5. Прогресс по каждому файлу                                    SSE run.progress / run.file, GET /runs/{id}
6. Сводка корпуса: статьи, факты, замечания, покрытие полей     GET /corpora/{id}/summary
7. Таблица фактов корпуса: поиск, фильтры («КПД > 20 % перовскиты»), сортировка, пагинация   GET /facts/table
8. Источник на странице PDF с подсветкой                        GET /papers/{id}/anchors, /pages/{n}
9. Замечания и разбор человеком                                 GET /issues, POST /issues/resolve, POST /facts/{id}/…
10. Экспорт: 7 CSV сдачи + проверка check_submission.py       POST /exports {format: "submission", validate: true}, GET /passport
    Без интерфейса — то же одной командой:                      faktura extract --domain solar --in ./test --out ./out --check docs/case5/tools/check_submission.py
```

Дополнительные сценарии поверх того же конвейера: загрузка одной статьи и её разбор (§4.6), вопросы в чате (§4.5, §12), сравнение и граф связей.

Ключевые понятия:

| Понятие | Что это | Сущность API |
|---|---|---|
| **Корпус** | Набор PDF одной области (или `auto`), который прогоняется целиком | `Corpus`, `CorpusFile` |
| **Прогон** | Пакетная обработка корпуса: все файлы / новые / выбранные / упавшие / только нормализация / только проверки | `BatchJob` |
| **Профиль извлечения** | Список полей для извлечения (паспорт в рабочей форме) и включённые правила | `ExtractionProfile` |
| **Коллекция** (предметная область) | `solar` — «Солнечные элементы», `rag` — «RAG и поиск». Задаёт схему извлечения, параметры, единицы и проверки | `Collection` |
| **Проект** | Папка с чатами, у проекта одна коллекция. Вопросы в проекте ищут только по статьям проекта | `Project` |
| **Чат** | Либо разбор одной статьи (`kind: paper`), либо вопросы к коллекции (`kind: ask`). Чат без проекта — в «Недавних» | `Chat`, `Turn` |
| **Статья** | Публикация + PDF + ход разбора | `Paper` (= `publication` из ТЗ) |
| **Образец / строка** | Строка таблицы статьи: прибор (solar) или конфигурация (RAG). Особая строка `*` — «все образцы» | `Row` |
| **Факт** | Одно значение одного параметра у одного образца с местом в источнике, исходной и нормализованной записью, уверенностью и статусом проверки (`new / accepted / rejected`) | `Fact` |
| **Замечание** | Результат правила проверки: правило, уровень, связанные факты, места в PDF. Разбирается человеком (`fixed / ok`), исходная запись не удаляется | `Issue` |
| **Утверждение** | Фраза в тексте статьи («наилучшие характеристики у образца B»), которая сверяется с таблицей | `Claim` |

### 1.3. Экраны: данные и действия

Ссылки «→ §4.N» ведут в [spec/04-api.md](spec/04-api.md), «→ §13.N» — в [spec/13-corpus.md](spec/13-corpus.md). Экраны перечислены по важности.

#### Корпус (`/corpus`, `/corpus/:id`) — *в интерфейсе появится*, первый экран после входа

Показывает: корпуса команды (имя, область, файлов всего/разобрано/с ошибкой, фактов, открытых замечаний, идущий прогон с процентом); у выбранного корпуса — таблицу файлов (имя, статус `queued/processing/done/failed/skipped_duplicate`, этап, фактов, замечаний, ошибка), прогоны, сводку (покрытие полей, ненайденные поля, замечания по правилам), профиль полей.
Данные: сразу после входа — `GET /corpus/overview` (лёгкая сводка) → §13.8; по выбору корпуса — `GET /corpora/{id}/files`, `GET /corpora/{id}/summary`, `GET /corpora/{id}/runs`, события `run.*`.
Действия: создать корпус `POST /corpora`; загрузить папку / ZIP / список URL `POST /corpora/{id}/files`; «Прогнать всё» / новые / выбранные / упавшие / только нормализация / только проверки `POST /corpora/{id}/runs`; отмена `POST /runs/{id}/cancel`; повтор файла `POST /corpora/{id}/files/{file_id}/retry`; профиль полей `GET/PATCH /profiles/{id}`; экспорт набора `POST /exports`.

#### Таблица фактов (`/facts`) — *в интерфейсе появится*, основной экран данных

Показывает: все факты корпуса строками — поле, значение (как в статье / нормализованное), единица, статья, год, образец, страница, таблица/рисунок, статус проверки, уверенность, замечания; строка запроса с языком запросов и таблетками фильтров; фасеты; сортировка; постраничная подгрузка.
Данные: `GET /facts/table` → §13.7. Действия: принять / отклонить / исправить → §4.8; массово по фильтру `POST /facts/bulk`; открыть источник (PDF на странице с подсветкой) → `GET /papers/{id}/anchors`, `/pages/{n}`; экспорт выборки `POST /exports` со `scope.table_filter`.

#### Боковая панель (`components/Sidebar.vue`)

Показывает: закреплённые чаты; проекты (закреплённые сверху, затем по дате создания) с их чатами (первые N, «ещё»); «Недавние» — чаты без проекта, по `updated_at` убыв.; у чата статьи — точка уровня открытых замечаний и прогресс разбора; меню профиля (имя, инициалы, цвет).

Действия:
| Действие | Эндпоинт |
|---|---|
| «Корпус» (первый пункт) и «Таблица фактов» — появится | `GET /corpus/overview`, `GET /facts/table` |
| Новый вопрос (вне проекта / в проекте) → `/app/ask` | ничего; чат создаётся с первым вопросом → §4.5 `POST /chats/ask` |
| Загрузить PDF (в текущий проект или вне) | `POST /papers` → §4.6 |
| Переименовать чат / проект | `PATCH /chats/{id}`, `PATCH /projects/{id}` |
| Закрепить чат / проект | `PATCH /chats/{id} {pinned}`, `PATCH /projects/{id} {pinned}` |
| Переместить чат в проект / в «Недавние» | `PATCH /chats/{id} {project_id}` |
| Удалить чат (если чат статьи — удаляется статья с фактами) | `DELETE /chats/{id}`, «Вернуть» → `POST /chats/{id}/restore` |
| Удалить проект (чаты уходят в «Недавние») | `DELETE /projects/{id}`, «Вернуть» → `POST /projects/{id}/restore` |
| Создать проект / настройки проекта | `POST /projects`, `PATCH /projects/{id}` |
| «История» (список всех чатов) | `GET /chats` |
| Выйти | `POST /auth/logout` |

#### Новый вопрос в чате (`/app/ask`, `views/HomeView.vue`, `components/Composer.vue`) — дополнительный сценарий

Показывает: приветствие, счётчики выбранной коллекции («N статей, M фактов»), подсказки вопросов, выбор коллекции под полем ввода.
Данные: `GET /collections/{id}/stats` → §4.3.
Действия: задать вопрос → `POST /chats/ask` (создаёт чат и первую реплику, отдаёт поток ответа) → §4.5; прикрепить PDF → `POST /papers` → §4.6; перетащить PDF на окно → то же.

#### Главная проекта (`/p/:id`, `views/ProjectView.vue`)

Показывает: имя, описание (`note`), коллекцию проекта, список чатов проекта (у чатов статей — статус разбора, число открытых замечаний и их уровень), подсказки вопросов по статьям проекта.
Данные: `GET /projects/{id}`, `GET /chats?project_id=`, `GET /projects/{id}/suggestions`.
Действия: вопрос в проекте → `POST /chats/ask {project_id}`; загрузить PDF в проект → `POST /papers {project_id}`; переименовать / закрепить / удалить проект и чаты (как в боковой панели).

#### Чат статьи (`/c/:id`, `kind: paper`; `views/ChatView.vue`, `components/PaperReview.vue`, `FactsPanel.vue`, `PdfPage.vue`, `AddFact.vue`, `Coverage.vue`, `DeviceStack.vue`, `PaperLinks.vue`, `DupNotice.vue`, `Pipeline.vue`)

Две вкладки (на телефоне три: «Чат · Факты · Статья»), режим в адресе `?view=chat|facts|paper`.

**Пока идёт разбор:** этапы `Текст → Таблицы → Рисунки → Формулы → Нормализация → Проверка`, процент; если тема определена «наугад» — вопрос «Это про солнечные элементы или про RAG?»; если похоже на уже загруженную — строка «Похоже на «…» — уже есть в коллекции» с выбором «Оставить обе» / «Удалить новую».
Данные: `GET /papers/{id}` (поле `processing`), поток `GET /events` (SSE) или опрос `GET /papers/{id}/processing` → §4.6. Сменить тему → `PUT /papers/{id}/collection`; удалить дубликат → `DELETE /chats/{id}`.

**Вкладка «Разбор»** — слева панель фактов, справа PDF.
- Шапка: название, авторы, год, журнал, сводка качества (всего фактов, % с источником, % нормализованных, принято, открытых замечаний), полнота «найдено X из Y» → `GET /papers/{id}` (поля `quality`, `coverage_summary`).
- Панель фактов: вкладки «Все · Замечания», фильтр по статусу (новые / принятые / отклонённые), группы по образцам, у факта — значение, как напечатано, источник («т. 2», «текст», «рис. 3», «вручную»), уверенность тремя уровнями, пометка «2 значения» (таблица и рисунок расходятся), карточка «Подробнее»: цепочка нормализации, сверка рисунка с таблицей, замечания факта → `GET /papers/{id}/facts`, `GET /papers/{id}/issues?status=all`, `GET /facts/{id}/trace`.

## 1А. Кто за что отвечает

Команда и роли (распределение задач — [docs/TASKS.md](TASKS.md); при расхождении верна эта спецификация):

| Роль | Кто | Коротко |
|---|---|---|
| **Фронт** | фронт | Интерфейс: корпус, таблица фактов, статья с PDF, проверки, экспорт, паспорт. Только показывает готовое и собирает ввод человека |
| **Бэк** | Андрей | API, хранение по модели ТЗ, корпус и пакетный прогон (конвейер), проверки, экспорт и CLI, вход, журнал и отмена |
| **ML (извлечение)** — ML-1 | Иван | Отдельный Docker-контейнер `POST /ml/extract`: PDF → JSON со всеми полями из списка, со страницей, местом, bbox, уверенностью, `result_origin`. LLM через роутер (§7.0) |
| **ML (разбор, нормализация, связи, RAG)** — ML-2 | второй ML | Разбор PDF в «документ» (текст, таблицы, bbox, `needs_ocr`), тема статьи, модуль нормализации и словарь, скрипт оценки по эталону, связи статей, дубликаты, правила сопоставимости, агентный RAG по таблице фактов (опционально) |

Код ML-2 для нормализации, дубликатов и сопоставимости встраивается в конвейер бэка (Python-пакет или сервис `/ml/normalize`, §7.0) — поэтому поля, которые он считает, помечены в модели как **[BE]**: это вычисляется на стороне бэка детерминированно, автор алгоритма — ML-2. Пометка **[ML]** — значения, которые выдаёт модель (ML-1 или ML-2) в своём ответе.

**Статьи не сравниваются попарно.** Каждый PDF обрабатывается отдельно, почти все проверки идут **внутри одной статьи**. Между статьями есть только три вещи:
1. **сопоставимость** результатов — фильтр по правилам ТЗ (§5.3) при сравнении и поиске, а не проверка, создающая замечания;
2. **дубликаты** — одна и та же статья в корпусе (SHA-256, DOI, название);
3. **`result_origin = cited`** — значение процитировано из другой работы (и, если она есть в корпусе, ссылка `cited_publication_id`).

Граф связей (кто кого цитирует, общие материалы) — справочный экран, он не меняет данных и не порождает замечаний.

### 1А.2. Что фронт НЕ делает

В продукте фронт **не извлекает, не нормализует, не проверяет и не ищет** — он показывает то, что посчитали бэк и ML. В прототипе многое из этого сейчас считается в браузере; всё это **переезжает**:

|---|---|---|
| Разбор статьи: `buildFacts()`, разметка `[[B.bandgap|…]]` в `data.ts`, `figureFacts()` в `figures.ts`, имитация `uploadFiles()`/`runProcessing()`/`seedFor()` в `store.ts` | ML (извлечение) + бэк (сохранение, этапы) | `GET /papers/{id}` с `processing`, `GET /papers/{id}/facts`, события SSE `paper.progress` |
| Определение темы `detectTopic()` по словам в имени файла | ML (классификатор) + бэк (правило выбора) | `paper.collection`, `paper.topic_by` |
| Нормализация: `parseRaw()`, `normConditions()`, `fmt/fmtFull()` для показа значения факта, `display()`, `valueOf()` | бэк | `fact.normalized_value`, `fact.value`, `fact.display`, `fact.extraction_status` |
| Цепочка нормализации `normTrace()`, сверка `crossOf()` (`norm.ts`) | бэк | `GET /facts/{id}/trace`, `fact.cross` |
| Предпросмотр и угадывание для ручного факта `previewRaw()`, `guessFact()`, `pickValue()` | бэк | `POST /normalize/preview`, `POST /papers/{id}/facts/guess` |

### 1А.3. Что готовит ML и что с этим делает бэк

Коротко (полный перечень артефактов с JSON-схемами — [§7.2](spec/07-ml.md#72-артефакты-ml-перечень-и-json-схемы), обработка — [§7.4](spec/07-ml.md#74-что-бэк-делает-с-результатом-ml)):

| Артефакт | Кто готовит | Эндпоинт | Что бэк делает |
|---|---|---|---|
| A1. `topic` — коллекция, уверенность, ключевые слова, «в границах корпуса» | ML-2 | `/ml/parse` | выбирает коллекцию по правилу, пишет `topic_by` |
| A2. `document` — страницы, блоки, таблицы, рисунки, разделы, bbox, `needs_ocr` | ML-2 | `/ml/parse` | сохраняет разметку, рендерит страницы, строит текстовый индекс; передаёт документ ML-1 |
| A3. `publication` — название, авторы, год, DOI, журнал | ML-1 | `/ml/extract` | обновляет `Paper`, ищет дубликат |
| A4. `rows` (`devices` / `configs`) — образцы | ML-1 | `/ml/extract` | создаёт `Row`, `device` / `rag_config` |
| A5. `values` (`results`) — значения с происхождением | ML-1 | `/ml/extract` | нормализует, создаёт факты, якоря и записи ТЗ |
| A6. `entities` — материалы, условия, слои / наборы, эксперименты, конфигурации | ML-1 | `/ml/extract` | записи ТЗ, канон по словарю |
| A7. `claims` — утверждения текста и аннотации | ML-1 | `/ml/extract` | создаёт `Claim`, сверяет с таблицей (проверка внутри статьи) |
| A8. `references` и рёбра связей | ML-2 | `/ml/parse`, `/ml/links` | хранит, строит граф, сопоставляет `cited` |
| A9. `answer` — ответ чата (агентный RAG) | ML-2 | `/ml/ask` | проверяет каждое число ↔ `fact_id`, сохраняет, пересылает фронту |

Контракт `/ml/extract` — **ПРЕДВАРИТЕЛЬНЫЙ** (§7.0): будет сверен с итоговым JSON от ML-1; до этого бэк работает на моке по примеру из §7.0. После ML бэк выполняет этапы «Нормализация» и «Проверка», сохраняет всё одной транзакцией с `model_version`, ставит `processing = done` и отправляет `paper.done`.

## 2. Авторизация

### 2.1. Что обязательно

Обязателен **только вход по почте и паролю**. В интерфейсе (`views/LoginView.vue`) сейчас всё для вида; после подключения бэка форма «Вход» вызывает `POST /auth/login`.

Схема: **JWT access + refresh**.
- `access_token` — JWT, срок жизни 15 мин, в заголовке `Authorization: Bearer …`. Полезная нагрузка: `sub` (user_id), `wid` (workspace_id), `exp`, `iat`, `jti`.
- `refresh_token` — непрозрачная случайная строка (не JWT), срок 30 дней, хранится на сервере хешем, **одноразовый с ротацией**: каждый `POST /auth/refresh` выдаёт новую пару и гасит старый refresh. Повторное предъявление погашенного refresh гасит всю цепочку (признак кражи).
- Рекомендуемая доставка refresh — cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. Допустимо и в теле ответа, если фронт и API на разных доменах без общих cookie (тогда фронт хранит refresh в памяти + `localStorage` и сам отвечает за риски XSS). Выбор — см. «Спорные места».

#### `POST /auth/login`

```json
// запрос
{ "email": "team@faktura.ai", "password": "••••••••", "remember": true }
```
`remember: false` — refresh живёт 12 ч вместо 30 дней.

```json
// 200
{
  "access_token": "eyJhbGciOi...",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "rt_5Yk3...",          // если не через cookie
  "user": { "id": "usr_01", "email": "team@faktura.ai", "name": "Исследователь", "role": "Материаловед", "team": "Команда хакатона", "color": "graphite", "focus": "Перовскитные и тонкоплёночные солнечные элементы", "is_admin": false }
}
```

Ошибки:
| Код | `error.code` | `message` |
|---|---|---|
| 400 | `validation_error` | «Введите почту» / «Проверьте адрес почты» / «Введите пароль» (те же тексты, что на форме) |
| 401 | `invalid_credentials` | «Неверная почта или пароль» (одинаково для неизвестной почты и неверного пароля) |
| 403 | `account_disabled` | «Учётная запись отключена. Обратитесь к администратору» |
| 429 | `too_many_attempts` | «Слишком много попыток. Попробуйте через N мин» (`details.retry_after`, сек) — 5 неудачных попыток на почту за 15 мин, 20 на IP |

#### `POST /auth/refresh`
Тело `{ "refresh_token": "..." }` (или cookie). 200 — та же форма, что у login, без `user`. 401 `refresh_invalid` — «Сессия истекла, войдите снова».

#### `POST /auth/logout`
Гасит текущий refresh (и cookie). 204. С `{ "all": true }` — все сессии пользователя.

#### `GET /auth/me`
200 — объект `user` (как в login). 401 `unauthorized` — «Нужно войти».

Пароль: не короче 8 символов (как подсказывает форма), хеш argon2id или bcrypt (cost ≥ 12).

### 2.2. Учётные записи заводит бэк

Регистрация в интерфейсе **декоративная**: форма «Регистрация» (имя, почта, пароль ×2, согласие, индикатор надёжности) никуда не отправляется и в рабочей версии API не вызывает. Учётные записи создаёт бэк:

- CLI: `faktura users create --email team@faktura.ai --name "Исследователь" --role "Материаловед" --team "Команда хакатона" [--admin] [--password …|--generate]`, `faktura users disable|enable|reset-password --email …`, `faktura users list`.
- Или админский эндпоинт (только `is_admin`): `POST /admin/users`, `PATCH /admin/users/{id}`, `GET /admin/users`.
- Начальный админ — из переменных окружения при первом запуске (`FAKTURA_ADMIN_EMAIL`, `FAKTURA_ADMIN_PASSWORD`).

Опционально (фронт не вызывает): `POST /auth/register` — по умолчанию выключен и отвечает `403 registration_disabled` «Регистрация закрыта — учётную запись выдаёт администратор». Включается флагом `FAKTURA_ALLOW_SIGNUP=true`; тело `{name, email, password}`, ответ как у login, `409 email_taken`.

### 2.3. VK ID и Яндекс ID — только для вида

Кнопки «Войти через VK ID» и «Яндекс ID» показывают уведомление «— только для демонстрации». **OAuth сейчас не нужен.** Как подключить позже:

1. Зарегистрировать приложения в VK ID и Яндекс OAuth, получить `client_id/secret`, указать redirect `https://<host>/api/v1/auth/oauth/{provider}/callback`.
2. `GET /auth/oauth/{provider}/start?return_to=/app` → 302 на провайдера (Authorization Code + PKCE, `state` в подписанной cookie).
3. `GET /auth/oauth/{provider}/callback?code&state` → обмен кода, получение почты; таблица `user_identities(user_id, provider, subject, email, linked_at)`. Пользователь ищется по `(provider, subject)`, затем по подтверждённой почте. **Новых пользователей OAuth не создаёт**, пока регистрация закрыта: нет записи — `403 account_not_found` «Учётной записи с этой почтой нет».
4. Успех — выдаётся та же пара токенов (refresh в cookie) и 302 на `return_to`.

### 2.4. «Забыли пароль?» — только для вида

Ссылка ничего не делает. Сейчас сброс выполняет админ (`faktura users reset-password`). Позже: `POST /auth/password/forgot {email}` (всегда 204, письмо со ссылкой на 1 ч), `POST /auth/password/reset {token, password}`.

### 2.5. Права

**После входа.** Получив `200` от `POST /auth/login`, фронт ведёт на **`/corpus`** и сразу запрашивает `GET /corpus/overview` (лёгкая сводка, §13.8). Если при входе был сохранён адрес (`/login?next=/c/…`) — ведёт туда. Чат («Новый вопрос», `/app/ask`) — в боковой панели как дополнительный сценарий.

Пользователь видит данные своего рабочего пространства (команды). Внутри пространства все видят все статьи, факты, замечания, словарь и журнал (в журнале есть записи других людей: «Котова Е.»). Проекты, чаты и сохранённые виды — личные (`owner_id`), см. «Спорные места». Админ дополнительно управляет пользователями и эталонной разметкой.

Ключи API для внешних программ (на экране «Экспорт» примеры с `Authorization: Bearer $GEODE_KEY`): «в интерфейсе появится» — `GET/POST/DELETE /me/api-keys`, ключ работает как access-токен только на чтение (`GET`) и на `POST /papers`.

## 8. Нефункциональные требования

### 8.1. Загрузка PDF

| Параметр | Значение |
|---|---|
| Формат | только PDF: `Content-Type: application/pdf` **и** сигнатура `%PDF-` в первых байтах. Иначе `415 unsupported_file` «Можно загрузить только PDF» |
| Размер | до **50 МБ** на файл (`413 file_too_large` «Файл больше 50 МБ»); до 20 файлов за запрос, до 200 МБ на запрос |
| Страниц | до 300 (`422 too_many_pages`) |
| Зашифрованный / битый PDF | `422 pdf_encrypted` «PDF защищён паролем» / `422 pdf_broken` «Файл повреждён — не удалось прочитать PDF». Если ошибка обнаружилась уже в разборе — статья получает `processing.status = failed` с тем же кодом |
| PDF без текстового слоя (скан) | принимается; распознавание текста — дело ML (§7). Если ML не справился — `failed`, `pdf_no_text` |
| Дубликаты | точный — SHA-256 файла; смысловой — DOI, затем нормализованное название + год + первый автор (§4.6). Дубликат не отклоняется: статья создаётся с `dup_of` |
| Прогресс передачи | средствами браузера (XHR `upload.onprogress`); бэк поддерживает обычный multipart. Для файлов > 20 МБ — опционально tus/resumable |

### 8.2. Хранение

- Метаданные, факты, замечания, журнал — PostgreSQL (≥ 14). JSONB для `answer`, `layout`, `trace`.
- Файлы — S3-совместимое хранилище (MinIO локально): `papers/{workspace_id}/{paper_id}/original.pdf`, отрисованные страницы `.../pages/{n}@{scale}.webp`, выгрузки `exports/{id}.{ext}` (живут 24 ч). Ключи не угадываются; фронт получает файл через API (проксирование или подписанная ссылка на 5 мин).
- Удаление статьи — мягкое (`deleted_at`), окно восстановления 30 суток, затем физическое удаление файла и строк.
- Резервное копирование БД — ежедневно; хранилище — версионирование бакета.

### 8.3. Коды ответов и ошибок

| HTTP | `error.code` | Когда | `message` (пример) |
|---|---|---|---|
| 400 | `validation_error` | неверное тело/параметры; `field` указывает поле | «Поле «name» не может быть пустым» |

### 8.4. Локализация

Все `message`, названия правил, тексты замечаний, этапы разбора, подписи ответов чата — на русском, теми же формулировками, что в прототипе (`src/store.ts`, `src/checks.ts`). Числа в текстах для людей (`issue.text`, `answer.items[].text`) бэк форматирует по-русски: запятая, неразрывный пробел перед единицей («18,6 %», «1,10 В»); в числовых полях — числа. Заголовок `Accept-Language` на будущее (`en`) — пока игнорируется.

### 8.5. CORS и безопасность

- `Access-Control-Allow-Origin` — список из конфига (прод-домен фронта, `http://localhost:5173` для разработки), не `*`. `Allow-Credentials: true`, если refresh в cookie. Разрешённые заголовки: `Authorization, Content-Type, X-Request-Id, Last-Event-ID, Idempotency-Key`; открытые для чтения: `X-Action-Id, X-Request-Id, Content-Disposition`.
- `Idempotency-Key` на `POST /papers`, `POST /chats/ask`, `POST /chats/{id}/turns`, `POST /exports` — повтор с тем же ключом в течение 24 ч возвращает первый ответ.
- Цитаты и тексты из PDF отдаются как текст; фронт не вставляет их как HTML.
- Внутренние эндпоинты для ML (`/internal/ml/*`) — отдельный порт или сеть, аутентификация HMAC-подписью тела (§7).

### 8.6. Производительность

`GET /papers/{id}`, `/facts`, `/issues` статьи — до 200 мс; `/data/rows` по коллекции до 10 тыс. образцов — до 500 мс; первый байт ответа чата — до 1 с (событие `step`); проверки статьи пересчитываются синхронно после каждой правки факта (< 100 мс на статью), проверки коллекции — с кешем, инвалидируемым правкой.

## Спорные места

### Закрыто архивом организаторов (кейс 5)

- **Формат сдачи** — ровно 7 CSV шаблона, проверяет `check_submission.py` (§14). Больше не «предварительно».
- **FF в %**, единицы ASCII (`%`, `V`, `mA/cm2`, `Ohm*cm2`, `h`, `eV`, `nm`, `cm2`); `metric_value`/`metric_unit` = `normalized_*`. Прототип хранит FF долей — фронту перейти на % из API.
- **Порог `jv_consistency`** — 3 % относительных (в прототипе в статье было 0,3 п.п.).
- **`extraction_status`** — только `extracted`, `present_not_extractable`, `absent`. Правки и ручные факты — отдельные поля (`review_status`, `corrected_value`, `added_by`, `norm_status`).
- **Тандемы и расчётные работы** — `in_scope=false` с `exclusion_reason`, строк в других таблицах нет (как `D006`, `D016` в `dev_gold`). Правило `scope_out_of_bounds` убрано.
- **Имена проверок** — `check_name` из шаблона и эталона (§5.2); прежние имена прототипа (`physics`, `claims`, `records`, `unitsBad`…) остались только как группы интерфейса.
- **`aggregation`** — пусто, если в статье не сказано (342 из 659 строк dev_gold).
- **Повторы значения внутри статьи** — `duplicate_of`, отдельные строки со своим источником.
- **`publication_id`** — имя файла без расширения.
- **`measurements.device_id`** — несколько приборов через `;`.

### Остаётся открытым

1. **Контракт `/ml/extract` предварительный.** Принцип (строки 7 таблиц + `_bbox`, `_confidence`) зафиксирован, но точный JSON пришлёт ML-1; до этого бэк работает на моке по `dev_gold`. Не согласованы единицы и начало координат `_bbox`.
2. **Область 2 (RAG)** — архива нет; модель по полям ТЗ сохранена, формат сдачи и `check_name` уточнить, когда будет архив.
3. **Цитаты, которые pypdf видит иначе** (лигатуры, переносы, перемешанные колонки) — `check_submission.py` выдаёт предупреждение. Политика: для табличных значений писать «Table N, строка X» (скрипт их не проверяет), для текста — короткий фрагмент, найденный той же нормализацией (`quote_found`).
4. **Какие находки ML выгружать.** Предложение: все со `status` `open`/`fixed`; находки с `confidence < 0,5` — только в интерфейс.
5. **Строки `absent`.** Шаблон допускает, `dev_gold` их не содержит. По умолчанию не выгружаем; включается профилем.
6. **Ответы чата** — базовый режим бэка обязателен, агентный RAG ML-2 опционален (§12).
7. **Слои прибора в прототипе — заглушка** (`STACKS`); в продукте — от ML-1. Подложка в `layers` не пишется (шаблон) — интерфейс стека должен рисовать её отдельно или не рисовать.
8. **Личное и общее.** Статьи, факты, замечания, словарь, журнал — общие в команде; проекты, чаты, виды — личные.
9. **Refresh в cookie или в теле** — рекомендуется cookie.
10. **Основной поток пакетный**: экраны «Корпус» и «Таблица фактов» в интерфейсе появятся; `/app` → `/corpus`, чат — `/app/ask`.
11. **Статья в нескольких корпусах** — по умолчанию связывается, а не разбирается заново (`reuse_existing`).
12. **Повторный прогон и правки человека** — переносятся на совпавшие записи (прибор + показатель + измерение + место); несовпавшие исправления сохраняются как ручные факты.
13. **Нормализация: бэк или ML-2** — модуль пишет ML-2 (`faktura_norm`), исполняет бэк; поля помечены [BE].
