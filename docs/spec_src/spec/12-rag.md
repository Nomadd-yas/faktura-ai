# 12. RAG по корпусу (если понадобится)

[← К оглавлению](../BACKEND_SPEC.md)

> **[ОПЦИОНАЛЬНО].** Обязателен и достаточен **базовый вариант без RAG**: бэк сам отвечает по таблице фактов — разбор вопроса языком запросов (§4.11), выборка, шаблонный ответ со сносками на факты, как в прототипе (`src/query.ts`, режим `CHAT_MODE=rules`, §7.6).
>
> Основной вариант RAG — **агентный, поверх готовой таблицы фактов** (роль ML-2): модель сама строит запросы к таблице через инструменты и отвечает со ссылками на `fact_id` и страницы. Векторный поиск по тексту статей — **дополнение** (§12.6).
>
> Фронт во всех режимах одинаков: поток SSE §4.5, формат `Answer`, сноски на `fact_id`.

## 12.1. Базовый вариант (без RAG)

| Шаг | Кто | Как |
|---|---|---|
| Понять вопрос | Бэк | язык запросов: темы, «КПД выше 18», «после 2022», «противоречия»; намерение: сравнение, проверки, связи, полнота, структура, «лучший» |
| Найти | Бэк | SQL по фактам/строкам (корпус, проект или одна статья) |
| Ответить | Бэк | шаблоны: «Лучшее — КПД 19,0 %: перовскит, образец A. По запросу (…) нашлось N приборов…», пункты со сносками, итог, карточка, связанные вопросы |
| Отдать | Бэк | SSE |

Ни одного выдуманного числа (каждое — из факта), мгновенно. Минус — только шаблонные вопросы.

## 12.2. Агентный RAG по таблице фактов

Зачем: вопросы, которых шаблоны не покрывают — «какой метод нанесения поглотителя чаще даёт КПД > 20 %?», «в скольких статьях после 2022 нет условий измерения?», «средний Voc CIGS по годам», «какие конфигурации с reranker лучше без него и на сколько?».

```
Вопрос [USER] → Бэк: область (корпус / проект / статья), права, история чата
             → ML-2 агент (/ml/ask): план → вызовы инструментов (запросы к таблице) → результат → ответ с [[fact:…]]
                    ↕ инструменты: API бэка (основной) или pandas по CSV-выгрузке (локальный режим / CLI)
             → Бэк: проверка каждого числа ↔ fact_id, сноски, карточка → SSE фронту
```

### Данные, по которым работает агент
Готовая таблица фактов корпуса (§13.7) и связанные таблицы ТЗ — то же, что в экспорте (`results`, `devices`, `materials`, `measurements`, `layers` / `metric_results`, `rag_configs`, `datasets_tasks`, `experiments`, `issues`). Каждая строка несёт `fact_id`, `publication_id`, `source_page`, `source_table`/`source_figure`, `anchor_id`. Отклонённые факты в выдачу не попадают; исправленные — с действующим значением.

### Инструменты (tool calls)
Два способа доступа, одинаковые по смыслу:

**А. Через API бэка (основной, в продукте).** Бэк даёт агенту узкий набор инструментов — HTTP-эндпоинты только на чтение, с жёстко заданной областью (`scope` подставляет бэк, агент её не меняет):

| Инструмент | Эндпоинт | Параметры | Возвращает |
|---|---|---|---|
| `schema` | `GET /agent/schema` | — | таблицы, колонки, типы, единицы, значения enum (из паспорта) |
| `filter` | `POST /agent/query` `{op:"filter"}` | `table`, `where: [{col, op: "="\|"!="\|">"\|">="\|"<"\|"<="\|"in"\|"contains"\|"is_null", value}]`, `columns`, `order_by`, `limit` (≤ 200) | строки + `fact_id` + `source_page` у каждой |
| `group` | `POST /agent/query` `{op:"group"}` | `table`, `where`, `by: [col]`, `agg: [{col, fn: "count"\|"mean"\|"median"\|"min"\|"max"\|"sum"}]` | группы и агрегаты + `fact_ids` вошедших строк (до 50 на группу) и `n` |
| `top` | `POST /agent/query` `{op:"top"}` | `table`, `where`, `col`, `n`, `dir` | лучшие строки с `fact_id` |
| `get_fact` | `GET /agent/facts/{id}` | — | факт с происхождением и цитатой |
| `get_issues` | `POST /agent/query` `{op:"filter", table:"issues"}` | `where` | замечания с `fact_ids` |
| `comparable` | `POST /agent/comparable` | `fact_ids` | группы сопоставимости и причины (§5.3) |
| `search_text` (доп., §12.6) | `POST /agent/search` | `q`, `k` | фрагменты текста с `paper_id`, `page`, `anchor_id` |

Ограничения: только чтение; ≤ 12 вызовов на ответ; ≤ 200 строк за вызов; таймаут вызова 5 с; всё в области `scope`. Агрегат (`mean`, `count`) — это вычисленное число: бэк отдаёт его с `agg_id` и списком `fact_ids`, из которых оно получено, — на агрегат можно ссылаться `[[agg:…]]`.

**Б. pandas по CSV (локальный режим, отладка, CLI).** Агент получает папку выгрузки (§13.6: `solar/results.csv`, `facts.csv`, …) и выполняет код pandas в песочнице (без сети, только чтение, лимит 10 с и 512 МБ). Каждая строка CSV содержит `fact_id` и `source_page`, поэтому правила ссылок те же. Для продукта вариант А предпочтительнее (права, свежие правки, нет выполнения произвольного кода).

### Генерация
- Системная инструкция: отвечать по-русски, только по результатам инструментов; **каждое число — со ссылкой** `[[fact:<fact_id>]]` (или `[[agg:<agg_id>]]` для посчитанного); не пересчитывать единицы самостоятельно — брать `display`; если данных нет — «в корпусе этого нет»; при сравнении результатов разных статей — вызвать `comparable` и сказать о несопоставимости.
- Структура как `Answer`: вступление, пункты (по статьям), итог; опционально `card` (`compare|checks|graph|coverage|structure`) и до трёх связанных вопросов.
- Шаги для фронта (`steps`): «Разбираю вопрос», «Запрос к таблице: КПД > 20 %, перовскит», «Считаю среднее по 37 фактам», «Сверяю с источниками» — агент присылает их событиями `tool`.

### Потоковая отдача
Агент стримит бэку события; бэк проверяет каждый пункт целиком и только потом шлёт фронту `item` (§4.5). Шаги инструментов идут фронту как `step`.

## 12.3. Ссылки на факты и места в PDF

- Маркеры `[[fact:fct_…]]`, `[[agg:agg_…]]`, `[[chunk:chk_…]]` бэк заменяет сносками `[n]`.
- `Cite` для факта: `fact_id`, `paper_id`, `title`, `where` («стр. 4 · Табл. 2, строка B»), `quote`, **`anchor_id`** (`source_anchor`) — по нему фронт открывает статью на странице и подсвечивает bbox числа.
- `Cite` для агрегата: `agg_id`, текст «среднее по 37 фактам из 12 статей», `fact_ids` — фронт по нажатию показывает список источников.
- Если в пункте несколько чисел — несколько сносок (`AnswerItem.cites: [1, 2]`; поле `cite` — первая, для совместимости с прототипом).

## 12.4. Защита от выдумок (делает бэк)

1. **Каждое число** в пункте (кроме годов, номеров таблиц/рисунков/страниц, порядковых) должно иметь рядом маркер `[[fact:…]]` или `[[agg:…]]`.
2. Факт существует, в области `scope`, не отклонён; агрегат был реально выдан инструментом в этом ответе.
3. Число совпадает с `value` факта / значением агрегата с точностью округления `digits` (в канонической единице; «0,74» и «74 %» для Recall совпадают).
4. Нарушение → пункт **отбрасывается** (`RAG_UNVERIFIED=drop`, по умолчанию) или помечается `item.unverified = true` и показывается серым «не подтверждено» (`mark`). Если отброшено больше половины пунктов — ответ заменяется базовым (§12.1) с пометкой в `outro`.
5. Цитата `[[chunk:…]]` должна быть подстрокой текста фрагмента.
6. Карточка проверяется: статьи и строки существуют в области.
7. Все вызовы инструментов, отброшенные пункты, `model_version` логируются для оценки качества.

## 12.5. Контракт бэк ↔ ML-2 (`/ml/ask`)

### Запрос [бэк → ML-2]
`POST {ML2}/ml/ask` (`Accept: text/event-stream`)
```json
{ "request_id": "trn_9:v1", "question": "Сравни КПД перовскитов после 2022", "language": "ru",
  "scope": { "workspace_id": "ws_1", "corpus_id": "crp_solar", "collection": "solar", "paper_ids": null },
  "tools": { "base_url": "https://api/internal/agent", "token": "<короткоживущий токен только на чтение, только этот scope>", "allowed": ["schema", "filter", "group", "top", "get_fact", "get_issues", "comparable"] },
  "history": [ { "q": "Какие приборы лучшие по КПД?", "a": "Лучшее — КПД 21,3 %…" } ],
  "allowed_cards": ["compare", "checks", "graph"],
  "limits": { "max_items": 6, "max_tool_calls": 12, "timeout_s": 40 } }
```
Токен инструментов выдаёт бэк на один ответ (5 мин), он ограничен `scope` и только чтением.

### Вызов инструмента [ML-2 → бэк]
`POST /internal/agent/query`
```json
{ "op": "top", "table": "results", "where": [ { "col": "metric_name", "op": "=", "value": "PCE" }, { "col": "material_class", "op": "=", "value": "perovskite" }, { "col": "year", "op": ">", "value": 2022 } ], "col": "metric_value", "n": 5, "dir": "desc" }
```
→
```json
{ "rows": [ { "fact_id": "fct_stab_c_h0_pce", "publication_id": "pap_stab", "title": "Стабильность перовскитных элементов при 85 °C", "year": 2023, "device_label": "0 ч", "metric_value": 21.3, "display": "21,3 %", "source_page": 7, "source_table": "Табл. 2" },
           { "fact_id": "fct_mapbi_c_A_pce", "publication_id": "pap_mapbi", "year": 2024, "device_label": "A", "metric_value": 19.0, "display": "19,0 %", "source_page": 4, "source_table": "Табл. 2" } ],
  "total": 9 }
```

### Потоковый ответ [ML-2 → бэк]
```
event: tool
data: {"name":"top","summary":"Запрос к таблице: КПД, перовскит, после 2022"}

event: tool
data: {"name":"comparable","summary":"Проверяю сопоставимость 3 результатов"}

event: intro
data: {"text":"Среди перовскитов после 2022 года лучший КПД — 21,3 % [[fact:fct_stab_c_h0_pce]]."}

event: item
data: {"index":0,"head":"Стабильность перовскитных элементов при 85 °C (2023)","text":"образец «0 ч»: КПД 21,3 % [[fact:fct_stab_c_h0_pce]], после 1000 ч — 17,1 % [[fact:fct_stab_c_h1000_pce]]"}

event: item
data: {"index":1,"head":"Перовскитный солнечный элемент с КПД 18,6 % (2024)","text":"образец A: КПД 19,0 % [[fact:fct_mapbi_c_A_pce]]; в тексте статьи лучшим назван B — это отмечено замечанием"}

event: card
data: {"kind":"compare","ids":["pap_stab","pap_mapbi"],"rows":["h0","A"],"metric":"pce"}

event: outro
data: {"text":"Средний КПД по 9 приборам — 18,7 % [[agg:agg_7]]. Результаты сопоставимы: AM1.5G, 100 мВт/см²."}

event: done
data: {"followups":["Где данные не сходятся?","Связи этих статей"],"model_version":"ask-0.1","tool_calls":3}
```
Ошибка: `event: error`, `data: {"code":"timeout","retryable":true}` → бэк отвечает базовым вариантом и пишет `generated_by = "rules"`. Стоп: `POST {ML2}/ml/ask/{request_id}/cancel` при `POST /turns/{id}/stop`.

## 12.6. Дополнение: векторный поиск по тексту статей

Когда вопрос — не о числах таблицы, а о тексте («как объясняют рост Voc?», «какие ограничения метода указывают авторы?»), агент вызывает `search_text`.

| Что | Кто | Как |
|---|---|---|
| Индексация | ML-2 (чанки, эмбеддинги), бэк (когда и что, хранение) | после разбора статьи: абзацы из документа A2 по ~300–500 токенов с перекрытием 50; строки таблиц — отдельными чанками с `fact_ids`; у чанка `paper_id`, `page`, `section`, `anchor_id` |
| Хранилище | бэк | pgvector в PostgreSQL (или Qdrant); BM25 — полнотекстовый индекс PostgreSQL; фильтр по `workspace`, `corpus`, `paper_ids` обязателен |
| Поиск | ML-2 | гибрид BM25 (top 50) + векторный (top 50), слияние RRF, переранжирование кросс-энкодером → top 8 |
| Ссылки | — | цитаты `[[chunk:…]]` (подстрока чанка); числа из текста всё равно должны ссылаться на `fact_id` — правило §12.4 не ослабляется |

Индексация: `POST {ML2}/ml/index {paper_id, blocks:[{chunk_id, text, page, anchor_id}], table_rows:[{chunk_id, text, fact_ids}]}`; удаление — `DELETE {ML2}/ml/index/{paper_id}`.

## 12.7. Кто за что (RAG)
| Что | Фронт | Бэк | ML-2 |
|---|---|---|---|
| Базовый ответ | поток SSE, сноски | разбор запроса, SQL, шаблоны | — |
| Агент | шаги «Запрос к таблице…», пункты, сноски, подсветка bbox по `anchor_id` | инструменты `/internal/agent/*` (только чтение, область), токен на ответ, проверка чисел ↔ `fact_id`/`agg_id`, сноски, хранение, запасной базовый ответ | план, вызовы инструментов, текст с маркерами, карточка, связанные вопросы |
| Текстовый поиск (доп.) | — | хранение векторов и BM25, область | чанкинг, эмбеддинги, гибрид, переранжирование |
| Оценка | 👍/👎 и причина | хранит с `model_version` и журналом вызовов | использует для улучшения |
