# 7. ML — контракт между бэком и ML-сервисом

[← К оглавлению](../BACKEND_SPEC.md)

> **Этот раздел — про ML.** ML-сервис — отдельный процесс (свой репозиторий, своё железо). Бэк ставит ему задачи, принимает результат, проверяет, нормализует, считает проверки и хранит. Фронт с ML напрямую **не общается никогда**.
>
> Пометки: **[ML]** — приходит от ML-сервиса; **[BE]** — считает бэк.

Связанные разделы: OCR (сканы) — [§11, ПЛАНЫ](11-ocr.md); RAG-ответы чата — [§12, ОПЦИОНАЛЬНО](12-rag.md).

## 7.0. Контейнеры и роли (решение команды)

Две ML-роли (см. [TASKS.md](../TASKS.md)):
- **ML-1 — извлечение** (Иван): Docker-контейнер `faktura-extract`, `POST /ml/extract`.
- **ML-2 — разбор, нормализация, связи, RAG**: контейнер `faktura-parse` (`/ml/parse`, `/ml/links`, опц. `/ml/ask`) и Python-пакет `faktura_norm`, который бэк подключает в конвейер (или тот же контейнер с `/ml/normalize`).

Конвейер на каждый PDF (выполняет бэк):
```
бэк: PDF → ML-2 /ml/parse (документ, тема, needs_ocr, литература)
         → ML-1 /ml/extract (PDF + документ + список полей → значения)
         → нормализация (faktura_norm от ML-2)
         → проверки внутри статьи (бэк, §5)
         → сохранение, версии моделей
```

### 7.0.1. Контейнер ML-1 `faktura-extract`

> **Контракт `POST /ml/extract` — ПРЕДВАРИТЕЛЬНЫЙ.** Будет сверен с итоговым JSON, который пришлёт ML-разработчик (ML-1). До этого бэк работает на **моке** по примеру ниже (заглушка отдаёт строки `docs/case5/dev_gold/` для статей dev и пустой ответ для остальных). Принцип зафиксирован: **выход ложится 1:1 в 7 таблиц сдачи** (§14) — по сути это строки этих таблиц для одной статьи плюс `bbox` и `confidence` для интерфейса.

**Запуск.**
```
docker run -p 8001:8000 \
  -e ROUTER_URL=https://<routerai>/v1 -e ROUTER_API_KEY=*** \
  -e EXTRACT_MODEL=<модель в роутере> -e EXTRACT_TIMEOUT_S=300 -e EXTRACT_CONCURRENCY=2 \
  faktura-extract:0.3
```
LLM через роутер (routerai). `ROUTER_URL`, `ROUTER_API_KEY` — переменные окружения или аргументы (`--router-url`, `--router-api-key`). **Ключ в репозитории не хранится** (только `.env` вне git / секреты окружения), в логах маскируется. Бэк ключ роутера не знает.

**`GET /health`** → `200 {"status":"ok","model_version":"extract-0.3","router":"ok"}`; `503`, если роутер недоступен (бэк ставит прогоны на паузу).

**`POST /ml/extract`** — синхронный.

`multipart/form-data`:
| Поле | Обяз. | Описание |
|---|---|---|
| `file` | да | PDF |
| `publication_id` | да | имя файла без расширения (`P042`) — ML ставит его во все строки |
| `domain` | да | `solar` (область 2 — `rag`, формат уточнить) |
| `fields` | нет | список полей профиля (§13.3); без него — стандартный по шаблону |
| `document` | нет | «документ» от ML-2 (`/ml/parse`) — чтобы не разбирать PDF второй раз |
| `request_id` | нет | идемпотентность и логи |

Правила ответа:
- **`metric_value`, `metric_unit`, `normalized_value`, `normalized_unit` ML не заполняет** (может, но бэк перезапишет): нормализация — в конвейере бэка (§6). `raw_value`/`raw_unit` — дословно.
- **Без `source_page` значение не отдаётся** (кроме `absent`). `source_fragment` — дословная цитата со страницы; для ячейки таблицы допустимо «Table 4, B4».
- Неизвестное не придумывается: поля нет в статье — `null`; показателя нет — строки нет (или `absent`, если профиль требует явной отметки).
- **Классификация области — на ML** (ML-1 по тексту, может опираться на `topic` от ML-2): `in_scope=false` + `exclusion_reason` по разделу 3.1 условий (расчётная/модельная работа, тандем, нет изготовленных приборов) — тогда **все остальные массивы пустые**.
- Повторы одного значения внутри статьи — отдельные строки с `duplicate_of` (§3.6.1).
- Находки, которые видны только при чтении (`contradiction`, `ambiguity`, `typo`, `possible_swap`, `derived_values`, `figure_only`, `cited_in_table`, `text_mix`, `dedup_trap`, `measurement_conditions`) — в `issues` с цитатой. Правила по числам (`jv_consistency`, `voc_limit`, `range`, `eqe_consistency`, `champion_vs_mean`, `hysteresis_index`) ML может не делать — их считает бэк (§5).
- Показатели вне списка `metric_name` (`Voc_deficit`, `Jmpp`, …) — можно, с понятным именем.
- `_bbox` — в пунктах PDF; **начало координат уточнить с ML-1** (предварительно — левый верхний угол страницы). Бэк переводит в `rects` в долях страницы.

**Ошибки:** `400` (нет файла, неверный `domain`), `413` (> 50 МБ), `422 {"code":"pdf_no_text"|"pdf_encrypted"|"pdf_broken"}`, `429` (очередь полна, `Retry-After`), `502 {"code":"router_error"}`, `504 {"code":"timeout"}`. Тело — `{"code","message","retryable"}`.

**Таймауты и лимиты.**
| Параметр | Значение |
|---|---|
| Таймаут на стороне бэка | `EXTRACT_TIMEOUT_S` + 30 с (по умолчанию 330 с) |
| PDF | до 50 МБ, до 300 страниц |
| Параллельность | `EXTRACT_CONCURRENCY` запросов на контейнер; остальные — `429`; бэк держит не больше |
| Ретраи бэка | `429`, `502`, `504`, обрыв — до 3 раз (30 с, 2 мин, 10 мин); `422` — без ретраев |

**Версия модели.** `model_version` в каждом ответе и в `/health`; бэк пишет её в статью, каждый факт и `manifest.json`.

**CLI ML-1** (для отладки модели, TASKS): `extract --domain solar --in ./pdfs --out ./raw` — по JSON-файлу этого формата на PDF. Бэк умеет загрузить такую папку без вызова контейнера: `faktura import-raw --in ./raw --corpus crp_dev`.

### 7.0.2. Контейнер ML-2 `faktura-parse`

| Эндпоинт | Вход | Выход |
|---|---|---|
| `GET /health` | — | `{status, model_version}` |
| `POST /ml/parse` | multipart `file`, `domain_hint` | «документ» (страницы, блоки, таблицы с ячейками и bbox, подписи, разделы), `needs_ocr`, `topic` (`solar`/`rag`/не по теме + уверенность), список литературы |
| `POST /ml/links` | `{papers: [{paper_id, DOI, title, year, authors, references, materials}]}` | рёбра `[{from, to, kind: "cites"\|"shares_material"\|"shares_method"\|"external", evidence}]`, смысловые дубли статей `[{a, b, by: "doi"\|"title"\|"text", score}]` |
| `POST /ml/normalize` (если не пакетом) | `{domain, values: [{metric_name, raw_value, raw_unit, header_unit}]}` | `[{normalized_value, normalized_unit, norm_status, trace}]` |
| `POST /ml/ask` (опц.) | §12 | поток SSE |

Пакет `faktura_norm` (предпочтительно): `normalize(metric_name, raw_value, raw_unit, header_unit) -> NormResult`, `match_metric(text) -> metric_name | None`, `canon_material(text)`, `layer_function(text, position)`; словари — данные (YAML/JSON) с версией (`dictionary_version`).

**Скрипт оценки** (ML-2): `faktura-eval --gold docs/case5/dev_gold --pred ./out [--pdf ./dev] --json report.json` — precision, recall, F1 по `metric_name` из списка условий (прочие игнорируются), точность `source_page`, нормализации, `aggregation`, `result_origin`, `extraction_status`, `in_scope`, совпадение `issues` (`check_name` + `record_ids`). Правила сопоставления — §14.7. Бэк запускает его в `GET /checks/accuracy` и после прогона dev.

## 7.1. Что делает ML и что нет

| ML делает | ML не делает (это бэк) |
|---|---|
| Классифицирует область: `in_scope` + `exclusion_reason` по разделу 3.1 условий (ML-1), тему `solar`/`rag` (ML-2) | Выбор итоговой коллекции; не создаёт записей у статьи с `in_scope=false` |
| Разметка PDF: страницы, блоки, разделы, таблицы, рисунки, bbox | Хранение файлов, рендер страниц для фронта |
| Метаданные: название, авторы, год, DOI, журнал | Поиск дубликатов |
| Строки-образцы: приборы / конфигурации | Уникальные идентификаторы, связи с таблицами ТЗ |
| Значения как напечатано + параметр как назван + место + уверенность + `result_origin` | Сопоставление параметра по словарю, нормализация единиц (`norm_status`); `extraction_status` даёт ML |
| Сущности ТЗ: материалы, условия, слои / наборы, эксперименты, конфигурации | Канон по словарю, сборка записей ТЗ из фактов |
| Утверждения текста и аннотации | Сверка утверждений с таблицей |
| Список литературы и упоминания | Сопоставление ссылок со статьями коллекции, граф |
| Значения с графиков (оцифровка) | Сверка рисунка с таблицей |
| (опц.) Ответы чата по фактам — §12 | Проверка сносок, хранение версий, оценки |
| (планы) OCR сканов — §11 | Решение, нужен ли OCR |
| | **Все проверки §5** |

## 7.2. Артефакты ML: перечень и JSON-схемы

> **Главный контракт извлечения — §7.0.1** (строки 7 таблиц сдачи). Схемы A1–A8 ниже — расширенная форма для интерфейса (разметка документа, утверждения, литература, точные bbox). Где они расходятся с §7.0.1 и шаблоном сдачи, верны §7.0.1 и §14: словари, `extraction_status` (`extracted|present_not_extractable|absent`), `aggregation` (пусто, если не сказано), `scan_direction` (`reverse|forward|average`), единицы ASCII.

ML возвращает один документ `ExtractionResult`, состоящий из артефактов A1–A8 (можно частями — §7.3). Артефакт A9 (ответ чата) — отдельный вызов, §12. Все bbox — в долях страницы `{x, y, w, h}` от левого верхнего угла; страницы с 1; `confidence` — 0…1.

## 7.3. Задача разбора: обмен бэк ↔ ML

> **Основной режим — синхронные вызовы контейнеров** `/ml/parse` и `/ml/extract` из воркера бэка (§7.0). Асинхронный протокол с задачами и вебхуками ниже — на будущее (для длинных PDF и OCR); бэк реализует его, только если синхронный режим упрётся в таймауты.

### Постановка задачи [BE → ML] (асинхронный вариант)
`POST {ML}/v1/jobs`
```json
{ "job_id": "job_7Hk2", "paper_id": "pap_u5kq2x9a", "file_url": "https://storage/…/original.pdf?sig=…&exp=3600", "file_sha256": "9f2c…",
  "collection_hint": { "collection": "solar", "by": "project" }, "schema_version": "1.0",
  "collections": { "solar": { "params": ["pce", "voc", "jsc", "ff", "bandgap", "thickness", "conditions"] }, "rag": { "params": ["r5", "r10", "mrr", "chunk", "retriever"] } },
  "dictionary_version": "2026-11-20T08:00:00Z",
  "callback_url": "https://api/internal/ml/jobs/job_7Hk2", "priority": "normal", "options": { "ocr": "auto", "figures": true, "stream_partial": true } }
```
Ответ `202 { "ml_job_id": "mlj_91", "status": "queued", "eta_s": 40 }`.

- `collection_hint.by = "project"` — коллекция известна, ML не классифицирует, а извлекает сразу по её схеме (A1 всё равно возвращает `in_scope`, `keywords`).
- Очередь — на стороне бэка (таблица `ml_jobs` + воркер, или брокер Redis/RabbitMQ). Идемпотентность: повтор `POST` с тем же `job_id` возвращает ту же задачу.

### Статусы задачи
`queued → running → (partial)* → done | failed | cancelled`. Этап (`stage`) — `Текст | Таблицы | Рисунки | Формулы`.

### Прогресс и результаты [ML → BE]
Предпочтительно **вебхуки** на `callback_url`; запасной вариант — **опрос** `GET {ML}/v1/jobs/{ml_job_id}` каждые 2 с.

| Вебхук | Тело | Что бэк делает |
|---|---|---|
| `POST /internal/ml/jobs/{job_id}/progress` | `{ "stage": "Таблицы", "progress": 45 }` (процент работы ML 0–100) | `paper.processing.progress = progress × 0,8`, событие `paper.progress` |
| `POST /internal/ml/jobs/{job_id}/partial` | `ExtractionResult` с `partial: true` и готовыми артефактами (например, A1 + A3 после «Текст») | применяет то, что можно: тема (A1) → коллекция и `topic_by`; метаданные (A3) → название, дубликат по DOI. Факты из частичных результатов **не показываются** до финала |
| `POST /internal/ml/jobs/{job_id}/result` | полный `ExtractionResult` | §7.4 |
| `POST /internal/ml/jobs/{job_id}/failed` | `{ "code": "pdf_no_text", "message": "…", "retryable": false }` | ретрай или `processing.failed` |

Аутентификация вебхуков: заголовок `X-Signature: sha256=<HMAC(тело, общий секрет)>` и `X-Timestamp` (окно 5 мин). Бэк отвечает `204` быстро, обработку ставит в очередь; повтор того же вебхука идемпотентен (по `job_id` + тип + хеш тела).

### Ретраи и таймауты
- Таймаут задачи — 10 мин (300 стр.) / 3 мин (до 30 стр.). Нет прогресса 2 мин — бэк опрашивает; ML не отвечает — задача перезапускается.
- До 3 попыток с паузой 30 с, 2 мин, 10 мин для `retryable` ошибок (`ml_timeout`, `ml_overloaded`, 5xx). Неретраимые (`pdf_encrypted`, `pdf_broken`, `pdf_no_text` без OCR) — сразу `failed`.
- Пока ML недоступен — статья в `queued`, событие «Сервис разбора временно недоступен — статья встанет в очередь».
- **Частичный финальный результат**: если ML не справился, например, с рисунками — присылает `result` с `partial: false`, `stages_done` без «Рисунки» и `warnings`. Бэк сохраняет то, что есть, а в статье — замечание `info` «Рисунки не разобраны».

### Версия модели
- `model_version` (и `schema_version`) приходит в каждом результате; бэк пишет её в `paper.model_version` и в каждый факт.
- Новая модель → `POST /admin/reprocess {model_version}`: статьи перезапускаются; правки человека переносятся на совпавшие факты (`row_id + param + source_kind`, значение в пределах 0,5 %), несовпавшие исправления сохраняются как ручные факты. Отчёт точности (`/checks/accuracy`) показывает версию.
- Несовместимая `schema_version` (мажорная) — бэк отклоняет результат `422` и задача `failed` с `ml_schema_mismatch`.

## 7.4. Что бэк делает с результатом ML

Этапы «Нормализация» и «Проверка» на экране — это бэк. Порядок:

1. **Валидация схемы** [BE]. JSON Schema §7.2; ссылки (`row_ref`, `value_ref`, `block_ref`, `table_ref`) должны существовать; `page ≤ page_count`; `rects` в 0…1. Битая запись отбрасывается с `warning`, остальное принимается. Если не прошла вся схема — `failed` (`ml_schema_mismatch`).
2. **Область и коллекция** [BE]. Если `publication.in_scope = false` — сохраняется только строка `publications` с `exclusion_reason`, остальное отбрасывается, статья помечается «вне области»; дальше шаги 3–10 не выполняются. Проект → его коллекция; иначе `topic.confidence ≥ 0,7` → `topic.collection`, `topic_by = text`; иначе выбранная пользователем, `topic_by = guess` (интерфейс спросит). `other` с высокой уверенностью → `in_scope = false` с `exclusion_reason` (замечаний не создаётся).
3. **Метаданные и дубликаты** [BE]. Обновить `title`, `authors`, `year`, `doi`, `journal`; поиск дубля (§4.6).
4. **Строки** [BE]. `row_ref` → `row_id` (метка строки, очищенная до `[A-Za-z0-9_-]`, уникальная в статье), записи `device` / `rag_config`.
5. **Сопоставление параметров** [BE]. `param_raw` → ключ по словарю (§6.3); `param_hint` ML — только если словарь не дал ответа **и** единица совместима с параметром; иначе — в `unmapped_values`.
6. **Нормализация** [BE] (§6): `normalized_value`, `normalized_unit`, `norm_status`, `metric_value`/`metric_unit` (= нормализованным), `display`; `extraction_status` не меняется.
7. **Якоря** [BE]: из `place` — `Anchor` с `rects`; связь с блоком; `spans` в блоках для подсветки в тексте.
8. **Факты и записи ТЗ** [BE]: факт на каждое значение; сборка `material`, `measurement`, `device`, `layer`, `result` / `dataset_task`, `experiment`, `rag_config`, `metric_result`; `cited_reference_n` → `cited_publication_id` через A8.
9. **Литература и граф** [BE]: сопоставление ссылок со статьями коллекции и внешними работами (DOI → arXiv → нормализованное название + год), `PaperEntity` по словарю.
10. **Проверки** [BE] (§5) — все правила статьи и коллекционные.
11. **Сохранение** [BE] — одной транзакцией; повторный результат той же задачи заменяет предыдущий (идемпотентно); при перезапуске разбора — перенос правок (§7.3).
12. **Готово** [BE]: `processing = done, 100`, событие `paper.done` с числом фактов и замечаний; строится текстовый индекс для поиска (и, если включён §12, — RAG-индекс).

## 7.5. Определение темы статьи и коллекции

| Шаг | Кто | Что |
|---|---|---|
| Загрузка в проект | [BE] | коллекция проекта, `topic_by = project`; ML не классифицирует |
| Загрузка вне проекта | [BE] | временно — выбранная коллекция, `topic_by = guess` |
| После «Текст» | [ML] | A1: `collection`, `confidence`, `topics`, `in_scope` (по первой странице и аннотации) |
| Решение | [BE] | `confidence ≥ 0,7` → `text`; иначе остаётся `guess`, интерфейс спрашивает «Это про солнечные элементы или про RAG?» |
| Человек выбрал | [USER] → [BE] | `PUT /papers/{id}/collection` → `manual`, перезапуск разбора по схеме коллекции |
| Темы для фильтров | [BE] | по словарю тем коллекции (`topics[].pattern`) по названию и ключевым словам; `topics` от ML — дополнительно |

## 7.6. Ответы в чате

Два режима, выбирается настройкой бэка `CHAT_MODE=rules|ml`:

- **`rules`** (базовый, обязательный) [BE]: детерминированные ответы, как в прототипе (`src/query.ts`): разбор вопроса языком запросов (§4.11), намерение (сравнение / проверки / связи / полнота / структура / «лучший»), выборка строк, текст по шаблонам, сноски на факты, карточки. ML не нужен.
- **`ml`** (опционально) — агентный RAG ML-2 поверх таблицы фактов: модель строит запросы к таблице через инструменты бэка (фильтр, группировка, выборка) и отвечает со ссылками на `fact_id` и страницы; векторный поиск по тексту — дополнение. Контракт `/ml/ask`, инструменты и защита от выдумок — [§12](12-rag.md).

В обоих режимах фронт получает одинаковый поток SSE (§4.5) и одинаковый формат `Answer`.
